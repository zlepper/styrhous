# Styrhous

Rust/egui desktop UI for exploring Kubernetes clusters. The UI runs separately from
Kubernetes I/O: a background worker owns cluster connections and watchers, while the
UI receives `WorkerResult` updates and sends `WorkerCommand`s.

## Development


```bash
# Build or run the app
cargo build
cargo run -p styrhous
```

For a local Kind cluster with resource-usage metrics, prepare the shared test cluster first:

```bash
bash scripts/ensure-kind-cluster.sh
cargo run -p styrhous
```

## Testing

Use nextest for all normal test runs. Do not use `cargo test` for the package test suite.

```bash
# Entire application suite
cargo nextest run -p styrhous

# One test
cargo nextest run -p styrhous test_ui_flow

# Update egui snapshot fixtures intentionally. Only do this once the ".new" files generated by tests are actually satisfactory.
UPDATE_SNAPSHOTS=1 cargo nextest run -p styrhous
```

`egui_kittest` snapshots live in each crate's `tests/snapshots/` directory. Review generated
`*.new.png` and `*.accessibility.new.txt` files before accepting them; never update snapshots
merely to make a test pass. Accessibility snapshots expose the AccessKit hierarchy plus each
node's logical egui-point bounds, and are useful for reviewing alignment and placement. Use the
project's `harness.ui_harness(...)` helper for every new snapshot so the pixel and accessibility
fixtures are always checked together. Its default pixel threshold is 2.1 with no failed pixels.
It also rejects meaningful same-layer accessibility-node overlap, including overflowing text runs;
popup and blade layers are detected automatically. Disable that check only for an explicitly
intentional same-layer collision with `HarnessSnapshotOptions::check_illegal_overlaps(false)`.

### Pre-commit hooks

Never bypass pre-commit hooks (including with `git commit --no-verify`). If a hook fails,
investigate and correct the underlying failure before committing.

### GitHub CLI from sandboxed agents

Request command approval escalation for authenticated `gh` commands and GitHub SSH
operations. The sandbox can report a valid keyring login as an invalid token or an
unreachable API. Retry with escalation before asking for reauthentication; never
print credentials or token values.

### UI tests

When matching a UI to a design oracle, use Kineprism's `compare_ui_images` for the
primary comparison report and its generated artifacts. Use
`scripts/compare-oracle-snapshot.sh` or `scripts/review-oracle-diff.sh` only as
supplementary ImageMagick/Codex CLI visual review tooling; do not use their metrics
as the acceptance criterion.

Harbour oracles are rendered from the design HTML by `scripts/design-oracles/` (see its README);
`scripts/design-oracles/compare.sh [ID…]` runs Kineprism for the boards in
`docs/design-oracles/harbour/manifest.toml` (preferring a pending `.new.png`) and writes
`target/design-oracles/scoreboard.md`. The `CAL` calibration board sets the pixel-match bar.

Whenever an accessibility snapshot changes, take a look at it, and make sure things actually line up. For example:
* Check that things that are "together" shares the same height or are centered properly with each other
* Check that icons and text in boxes is actually positions the expected way in those boxes, usually vertically centered
* Check that there is a proper margin around elements or between elements as necessary so things maintain a nice coherence.

#### General ui test rules
* Only ever use `accesskit_click` while troubleshooting. It should _never_ be in the final test code, as it might mask laying issues.

### Kind-backed integration tests

`test_real_cluster_connection`, `test_resource_watcher_integration`, and
`test_resource_actions_integration` are regular nextest tests. `.config/nextest.toml`
runs `scripts/ensure-kind-cluster.sh` once before the matching Kind tests. The
tests run in parallel; each mutable test owns a unique `styrhous-it-*` namespace and
holds a `flock` lease on it (`NamespaceLease`; `scripts/lib/kind-namespace-leases.sh`)
while it exists. The script removes only test namespaces whose lease it can take, so
leftovers of crashed runs are cleaned up while concurrent test runs (e.g. from several
worktrees) keep their namespaces. Create test namespaces only through
`IntegrationNamespaceFixture` so they get a lease.

When running Kind-backed tests from a sandboxed agent, request command approval
escalation for the nextest command. Rootless Podman needs to create a user namespace,
which the Linux sandbox blocks even when its runtime directories are writable.

The script uses the default cluster/context pair (`kind` / `kind-kind`): it creates a
missing cluster, starts existing Kind node containers, exports its kubeconfig, and waits
for the API server, nodes, and CoreDNS. It leaves the cluster running. A pre-existing,
unhealthy cluster is reported as a failure rather than deleted or recreated.

These tests use the real local Kubernetes cluster and may create, edit, or delete
their own test resources. Keep fixtures isolated to their unique namespace and do
not mark the tests `#[ignore]`.

## Architecture

- `crates/styrhous/src/ui.rs`: `MyEguiApp<W: WorkerTrait>`, UI state, accessibility-driven UI
  tests, and snapshot tests.
- `crates/styrhous/src/worker.rs`: background Tokio worker, command/result channel types, and
  `MockWorker` used by deterministic UI tests.
- `crates/styrhous/src/cluster_connection_manager.rs`: kubeconfig discovery, cluster
  connections, namespace/API discovery, and resource watchers.
- `crates/components/`: reusable egui components and their snapshot tests.

For UI tests, inject `MockWorker` and drive `WorkerResult` values through the harness.
Use a real `Worker` only when testing the Kind integration path.

## Project conventions

- The UI follows the Harbour design (`docs/design-oracles/harbour/`). Reuse the components in
  `crates/components` whenever they fit instead of one-off widget styling.
- Colours come from theme roles: read them with `ui.tokens()` (`design::theme::ThemeExt`), never
  from literals. Colour values exist only in `design::palette`; a guard test
  (`crates/components/tests/colour_guard.rs`) rejects them anywhere else. Wrap blades, dialogs,
  popovers, cards and sidebars in `theme::scope(ui, ThemeScope::…, …)` so overrides re-point.
  Change the theme only with `theme::switch(ctx, theme)`, which updates egui's visuals too.
  Use `Theme::tone(Tone::…)` for status colours, `design::stroke` for strokes, and
  `raised_frame`/`overlay_frame`/`popover_frame`/`WorkspaceCard` for elevated surfaces and cards.
  In tests that assert which role something paints with, install
  `test_support::distinct_role_theme()` so roles that share a palette entry are told apart.
- Set text with `design::type_scale` roles (`BODY`, `UI`, `META`, `CAPTION`, `TITLE`, `MONO`, …):
  `role.text(ctx, …, color)` for widget text, `role.rich_text(ctx, …)` for single centred lines,
  `role.galley(…)`/`role.label(…)` for CSS line boxes, and `role.label_on_baseline(…)` for rows
  that mix roles on one baseline. Display sizes are `const` roles (`DIALOG_TITLE`, `CARD_TITLE`).
  Fonts are Figtree, Bricolage Grotesque (one optical-size instance per display size), IBM Plex
  Mono and IBM Plex Sans Condensed (`design::fonts`); never synthesise bold.
  DejaVu Sans (Mono) is the fallback for other symbols and scripts; `tests/glyph_guard.rs` fails
  on a literal character no family can draw.
- Users can theme the app with an optional `theme.toml` in the eframe data directory
  (`~/.local/share/styrhous/theme.toml` on Linux), polled once a second by
  `ui/theme_file.rs`. It extends a built-in theme and overrides `[palette]` hex colours,
  `[roles]`/`[terminal]` palette names and `[components]` role names; see `docs/theming.md`,
  whose key reference is generated and checked by a test. The design's example is
  `crates/components/src/design/theme/harbour-dark-hc.toml`.
- Use `design::{space, radius, size, elevation}` for spacing, radii, dimensions and shadows. Do
  not hardcode reusable visual constants in screens or components; keep only feature-specific
  geometry (for example, animation or panel dimensions) local to its owner.
- Prefer behavior-focused tests and real interactions; mock only external, uncontrollable
  processes.
- Keep UI and Kubernetes operations separated through the worker commands/results.
- API resources and namespaces are keyed using the project helper types (`ApiResource`,
  `MinimalNamespace`, and `SortedName`); preserve their ordering/display semantics.
- Breaking changes are permitted: this project has no external users yet.

### Licensing Worker

The licensing service is one TypeScript Cloudflare Worker (`licensing/worker`) that serves the
API, the `/desktop/v2` protocol, and the static SvelteKit portal (`licensing/portal`). State lives
in D1. See `licensing/README.md` and `licensing/desktop-protocol.md`.

```bash
cd licensing/worker
npm ci
npm run check   # wrangler binding types + tsc
npm test        # vitest inside workerd with a real local D1
npm run dev     # builds the portal, then serves everything on the Vite dev server
```

- Keep licensing application and infrastructure artifacts under `licensing/`.
- Define the schema in `src/db/schema.ts` and generate migrations with `npm run db:generate`.
  There is no deployment to preserve yet, so regenerate the single initial migration instead of
  stacking migrations until the first production deploy.
- Commit each mutation's writes in one atomic D1 batch. Enforce invariants that concurrent
  requests could race inside the writing statement itself (unique indexes, `insertWhere`, or
  guarded `UPDATE … WHERE`), and map unchanged rows to the matching `reasonCode`. Put
  `auditInsert` directly after the statement it records.
- Validate request shapes with zod via `validate(...)`; keep business rules in their feature module.
- Tests call the Worker through `exports.default.fetch` against real local D1. Replace only
  third-party HTTP services (Stripe, OAuth providers) with `FakeUpstream`/`FakeStripe`, and the
  email binding with a spy. Do not add interfaces only to make code testable.
- The protocol fixtures in `licensing/protocol-fixtures` are shared with the Rust client and are
  reproduced byte for byte by the Worker tests; change them only together with the client.
- Never log credentials, secrets, invitation secrets, or email addresses.
- Deployment is Cloudflare Workers Builds on pushes to master; GitHub Actions only validates.
- Ordinary validation workflows run on pushes. Avoid duplicate PR/manual validation runs and
  explicit teardown of disposable hosted runners.

## Post-changes review
Once a changeset is done, use a set of sub agents to review for each of these things:
1. A critical code review agent. The agent should especially focus on possible bugs and edge cases. 
2. Look for possible duplicated code within the project and opportunities for refactoring and
extraction of shared behavior and/or components. The agent should also check for coding 
patterns that could be done better or cleaner by using common language abstractions (Such as
default spreads)
3. Focus on test handling. Are the changes well enough covered by tests? Especially consider
adding snapshot tests for better coverage.
4. If a UI snapshot have changed, have an agent check the related accessibility snapshots for
alignment of elements. Focusing on things that are supports to be aligned which each other actually being
aligned horizontally/vertically as relevant.

All of those agents can be launched in parallel if the harness supports it.

## Other notes

* Do not worry about running out of context. When you are working on a task, keep working until it
is actually complete. The context will auto-compact if necessary.
* If a test fails during a commit, rather than just retrying and calling it "good enough" actually
investigate and fix the test so it stops being flaky. And just changing test parallelism is not a fix.
If reducing parallelism fixes the issue, then it means the test has some bad state handling.
